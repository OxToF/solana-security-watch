What Anchor checks for free: reviewing Orca's Pinocchio fast path

Orca Whirlpools now routes six liquidity instructions through hand-written Pinocchio handlers. Dropping Anchor saves compute, and removes every check Anchor generates for you. We went through the six handlers to see whether each check came back by hand. It did. Here is how we checked, the one gap we sent upstream, and a checklist for your own port.

The instructions on the fast path

  • increase_liquidity and increase_liquidity_v2
  • decrease_liquidity and decrease_liquidity_v2
  • reposition_liquidity_v2
  • increase_liquidity_by_token_amounts_v2

Everything else, including swaps, still goes through Anchor. When a team drops Anchor on a hot path, the only security question that matters is simple to ask and slow to answer: was every implicit check re-implemented by hand?

The method: list what Anchor gave you, then find each check

A Pinocchio handler receives raw AccountInfos. Every line below has to come back as explicit code, and every missing line is a potential account substitution bug, the classic Solana critical.

What we found

Loading accounts. Owner and discriminator are re-checked before any cast. For token accounts, the token program is not taken from the caller: it is derived from the account owner by its last byte (0xa9 for SPL Token, 0xfc for Token-2022). Multisig-sized accounts (355 bytes) are rejected where a token account is expected.

Signer, writable, program ID. The account iterator enforces each constraint at the moment the account is pulled, not in a later check that can be forgotten.

Relations, the part that usually breaks. Every handler re-establishes what has_one would have given:

  • the position belongs to this whirlpool;
  • the position NFT matches the position mint and holds exactly 1 token;
  • the caller is the position owner or its delegate, and actually signed;
  • the token vaults are the whirlpool's own vaults;
  • on v2 instructions, the token mints are the whirlpool's mints;
  • the tick arrays are owned by the program, carry the right discriminator, and point back to this whirlpool.

The lock check is present on decrease: a locked position cannot be drained through the fast path.

Edge cases.

  • Lower and upper ticks in the same tick array. Rust will not borrow the same account mutably twice. The loader detects the case by key and hands out one mutable reference. Resizing reads the current data length each time, so two tick initializations in one array grow it twice, as expected.
  • Reposition. The netting of old and new range is bounded on both sides: a minimum on the full decrease, a maximum on the new range including fees.
  • increase_liquidity_by_token_amounts_v2, the only handler with no Anchor original. It computes with transfer-fee-excluded amounts, then re-checks the fee-included amount against the user's maximum.
No missing owner check, no missing signer, no unbound relation. That is consistent with the program's audit history, and it is what a careful port looks like.

The one gap: a layout invariant nobody enforced

Pinocchio handlers skip deserialization by casting account bytes straight to a struct:

let tick_array = unsafe { &*(data.as_ptr() as *const MemoryMappedDynamicTickArray) };

There is no length check on that cast. It is correct today because of three invariants:

  1. each MemoryMapped* struct has exactly the byte size of its Anchor account;
  2. each struct has alignment 1 (only byte arrays inside);
  3. dynamic tick arrays grow from 148 to 10,004 bytes as ticks are initialized, and the full-size struct still fits: even the smallest account plus the 10,240 bytes of realloc padding the runtime maps after account data covers 10,004 bytes, with 236 to spare.

All three hold. None was written down in code. A new field on the Anchor side, or a change to the tick size constant, would compile without a word and turn the cast into an out-of-bounds read.

This is not exploitable and not a bounty finding. It is a future-proofing gap, so we sent the fix upstream: compile-time assertions on all five memory-mapped account types that fail the build if any invariant breaks, proven to fire by mutating a constant and a struct. orca-so/whirlpools#1408

A detail worth knowing if you do the same. Our first version put the assertions right under each struct, and the compiled program changed. Rust embeds file:line in panic locations, so inserting lines mid-file shifts every line after it, and the binary with it. Appending the assertions at the end of each file gave a byte-identical .so. For a "no bytecode change" PR: append, do not insert, and compare hashes. Never compare sizes, a different binary can have the same size.

Not covered

We reviewed the six Pinocchio liquidity handlers and the shared code they rely on. We did not fully cover the swap path (still Anchor, and the most audited part of the program), the details of dynamic tick array rent accounting, or the Token-2022 transfer fee arithmetic.

A checklist for your own Pinocchio port

  1. Write down the full Anchor constraint list for each instruction before deleting it. That list is your test plan.
  2. Re-check owner and discriminator before every cast. Never cast first and check later.
  3. Derive program IDs from account owners instead of trusting a program account passed by the caller.
  4. Re-establish every has_one as an explicit comparison. Grep the old code for has_one and constraint, then find the matching line in the new code, one by one.
  5. Handle the same account passed twice on purpose: by key comparison, or by explicit rejection.
  6. Assert struct layouts at compile time: size, alignment, and the realloc margin for any account that grows.
  7. Mutation-test every guard. A check you have never seen fail is a check you have not proved.
